# 審查紀錄

App 完成後交付獨立審查，本檔記錄找到什麼、為什麼會漏、以及怎麼修的。

審查日期：2026-08-15

---

## 為什麼「測試全綠」在這裡毫無意義

第一輪審查前的狀態：`flutter analyze` 零問題、71 個測試全過、實機走完每個畫面沒有 crash。

而三個 **CRITICAL** 等級的缺陷全都活在那底下。

原因單一且可指認：**`DemoTransport` 比真實 ELM327 寬容**。測試只證明了 App 能正確處理模擬器產生的資料，而模擬器產生的資料在五個關鍵處與真車不同：

| 真實 ELM327 | 修正前的 `DemoTransport` |
|---|---|
| 多幀回應開頭有總長度行（`014`、`00A`） | 沒有 |
| 批次多 PID 回應會超過單幀而變成多幀 | 永遠單行 |
| `ATE0` 生效前會回音每個指令 | 從不回音 |
| 會發出 `SEARCHING...`、`DATA ERROR`、`BUS BUSY`、`STOPPED` | 一個都不發 |
| 舊協定的 Mode 03 沒有數量位元組 | 永遠有 |

**修正方向不只是補程式碼，而是讓模擬器變嚴格。** 現在 `DemoTransport` 會產生真實框架，於是這一類錯誤未來由測試套件抓，而不是由使用者的車抓。

## CRITICAL

### C1 · `ATCFC0` 關掉了 ISO 15765-4 必需的 flow control

設計筆記的 AT 初始化序列第 15 步要求送 `ATCFC0`。ELM327 datasheet 明載預設是 `CFC1`（開啟），關閉是給「非 OBD 的 CAN 實驗」用的。

**後果**：任何超過 7 個資料位元組的回應 —— VIN、多筆 DTC、fastMode 批次 —— ECU 送出 First Frame 後等一個永遠不會來的 Flow Control 幀，然後逾時。

**為什麼第一輪查證沒抓到**：我確認了「`ATCFC0` 是合法 AT 指令」。那是驗語法，不是驗語義。

**修**：從初始化序列移除。

### C2 · 多幀長度行被當成資料

`_parse` 剝掉非 hex 字元後把每一行串起來。多幀回應開頭的 `014` 貢獻三個 nibble，把整個 payload 位移半個位元組。

實測 datasheet 原文範例：VIN `1D4GP00R55B123456` 被讀成 `CDST3CS`。同一條路徑餵給 DTC 解碼，會產生車上根本沒有的故障碼。

**修**：改用白名單。

### C3 · 一半的 ELM327 狀態訊息被當成資料

錯誤矩陣只涵蓋 7 種訊息。datasheet 另外定義了 `BUS BUSY`、`BUS ERROR`、`DATA ERROR`、`FB ERROR`、`LV RESET`、`ACT ALERT`、`LP ALERT`、`ERR xx`。

未分類的訊息會被剝成 hex：`DATA ERROR` → `DAAE` → 兩個位元組 → 自訂 PID 讀出 218。Mode 03 收到 `DATA ERROR` 會解出 `U1AAE`。

**修**：`_parse` 只接受「整行都是 hex byte pair」的行，其餘一律視為狀態。這一招同時解掉 C2 與 C3，而且對未來韌體新增的訊息自動免疫。

## HIGH（節錄）

| 問題 | 後果 |
|---|---|
| 逾時後回應永久錯位 | 遲到的回應完成了下一個指令的 completer，之後每筆讀數都是上一輪的值，且不會自我修復 |
| Watchdog 在協定搜尋期間觸發 | `SEARCHING...` 後的靜默被當成斷線，把即將成功的連線拆掉 |
| `setHeader` 在 try 之外 | 一次逾時就讓輪詢迴圈永久結束，`isRunning` 說謊，儀表凍結 |
| fastMode 關閉後永不恢復 | `resetThrottle()` 沒有任何呼叫者 |
| `syncActivePids` 沒有任何呼叫者 | 連線中新增的儀表永遠顯示「—」，移除的仍在耗頻寬 |
| `Pid.id` 碰撞 | 匯入原廠 Torque CSV（含 `010C`）會頂掉內建的 Engine RPM 定義，連物理推算一起換掉 |
| DTC 讀取失敗顯示「無故障碼」 | 診斷畫面上的假安全訊息 |
| Android ≤ 11 未請求定位權限 | BLE 掃描回傳空清單且無錯誤，看起來像「附近沒有轉接器」 |
| 權限永久拒絕後無出路 | 沒有任何通往系統設定的入口 |
| BLE 掃描按鈕永久停在「搜尋中」 | 掃描串流從不關閉 |
| iOS 缺 `NSBluetoothAlwaysUsageDescription` | 首次使用藍牙即被系統終止 |

## MEDIUM（節錄）

- DTC 數量位元組用猜的：實測 `43 01 43 01 96`（舊協定的 `P0143` + `P0196`）被解成單一個不存在的 `C0301`。改由 `ATDPN` 回報的協定編號決定。
- 公式引擎 `%` 自成一級：`A/B%C` 被算成 `A/(B%C)`。改為與 `*` `/` 同級。
- 一元負號綁得比 `^` 緊：`-A^2` 得 `+9`。改為較鬆，並加負值哨符讓 `(-A)^2` 仍得 `9`。
- 缺位元組靜默補 0：截斷的轉速回應會讀成 1664 而非 1724，看不出異常。改為丟出例外。
- `accelMs2: 0` 讓慣性項完全失效，馬力只算風阻與滾阻。改為由車速歷程微分（EMA 平滑）。實測儀表板從 24 hp 變成 90 hp。
- 電壓只在握手時讀一次：發電機衰退看不出來。改為每 15 秒重讀。
- 匯入 CSV 每列各寫一次 SharedPreferences：O(n²)。改為單次寫入。

# 第二輪審查（獨立的第二位審查者）

第一輪的修正交給第二個獨立審查者驗證，並找第一輪漏掉的。結果：**7 HIGH + 7 MEDIUM**。逐條查證後 12 條確認為真、1 條部分正確、1 條有反證。

## 最嚴重的一條，是第一輪修正本身留下的洞

**協定在被「確定」之前就被使用。**

`ATSP0` 只是*武裝*自動搜尋 —— 真正的協定偵測要等第一個 OBD 請求才發生。握手期間讀 `ATDPN` 因此得到 `A0`（未決）。而我第一輪才加的 DTC 協定判斷 `protocolHasCountByte('A0')` 會剝掉 `A` 得到 `0`，`0 >= 6` 為 false → **在 CAN 車上用舊協定的框架規則解故障碼 → 產生車上不存在的故障碼**。

這是同一類錯誤的第二次出現：修正 A 建立在一個未經驗證的前提上。

**修**：把 `0100` 加入握手並標為關鍵步驟，`ATDP`/`ATDPN` 移到它之後。這一步同時是**唯一能證明車輛有回應的證據** —— 所有 AT 指令在電門關閉時都會正常回應，只有 `0100` 不會。模擬器也改為在探測前回 `A0`、之後才回 `A6`。

實機驗證：連線後協定顯示 `AUTO, ISO 15765-4 (CAN 11/500)` 而非未決的 `AUTO`。

## 其餘 HIGH

| 問題 | 後果 | 修法 |
|---|---|---|
| resync 送裸 `\r` | datasheet 定義為「重複上一個指令」，等於把剛逾時的指令再發一次 | 改為**不送任何東西**，等待實際的 `>` 出現才解除失步 |
| 換標頭與查詢是兩個佇列交易 | DTC/VIN/探索可能插進 `ATSH 7E1` 與查詢之間，在錯的 ECU 上執行 | 新增 `sendOnHeader()`，在同一個 chain slot 內完成 |
| teardown 可能拆掉新連線 | 斷線觸發的非同步 teardown 在 await 後重讀共用欄位，可能拆掉使用者剛建立的新 client | 所有 handle 在第一個 await *之前*取到區域變數 |
| DTC 接受非正向回應 | `NO DATA` → 空清單 → 假的「無故障碼」；`7F` 負向回應會解成假故障碼；Mode 04 沒收到 `44` 也回報成功 | 嚴格驗證模式位元組、拒絕 `7F`、清除必須收到 `44` |
| 重置類錯誤只分類不處理 | `LV RESET` / `ERRxx` 代表轉接器已重置並遺失所有設定，繼續輪詢等於用過期的假設解讀回應 | 觸發 session 層級的重建 |
| 失敗後舊讀數仍有效 | 錯誤只新增 fault，舊 `Reading` 留著，錶盤照顯示；斷線也不清空，A 車的數值會出現在連 B 車的過程中 | 失敗即作廢讀數；斷線送出空 snapshot；無讀數顯示 `--` 而非最小值 |

## MEDIUM 摘要

- 部分批次回應被當成成功：六個 PID 只回兩個時，其餘四個保留舊值且不重排。改為全有全無。
- 批次查詢未確認匯流排是 CAN 就送出。改為由協定編號閘控。
- 公式引擎仍把無效輸入變成數字：`SIGNED()` 越界、未解析的 `VAL{}`、除以零、非有限結果全部曾回傳 0；`2^3^2` 左結合得 64 而非 512。全部改為丟出例外，`^` 改右結合。
- Watchdog 把健康的靜默當成斷線（所有 PID 皆不支援時、或 App 從背景恢復時）。改為只在有未完成請求時判定。
- ELM327 偶爾插入的 NULL 位元組會讓整行不通過 hex 白名單。改為在兩處剝除。
- 編輯自訂 PID 會遺失 `variant`，改標頭/指令則產生重複項。改為保留識別並移除舊項。
- 儀表板固定兩欄，2.0 倍字級下反而讓數字更小。改為欄數隨字級縮放，極端設定下降為單欄大錶。
- 加速軌跡對每個 snapshot 都記點（含重複車速），會無限成長。改為只在讀數時間戳更新時記錄。

## 一條有反證的

審查者指出 320dp + textScaler 2.0 有「確定的 overflow」。我在 Galaxy S24 Ultra 上實測 320dp（density 160 與 240 兩種）搭配 2.0 倍字級，**logcat 零 RenderFlex/overflow**，文字正確換行。無障礙縮放被 `FittedBox` 抵銷的批評則成立，已依此調整欄數策略。

# 第三輪：驗證第二輪的修正

第二輪證明了「修正本身會引入新缺陷」不是偶然，所以第二輪的修正也做了一次針對性複查。找到一個。

**PID 編輯器再也存不了任何用到 `VAL{}` 的公式。**

第二輪把「未解析的 `VAL{}`」從回傳 0 改成丟例外 —— 這對執行期是正確的。但編輯器的即時預覽用的是一個全新的 `FormulaEngine`，快取必然是空的，於是任何含 `VAL{}` 的公式一律預覽失敗 → 儲存鈕永久停用，而說明文字還明寫支援 `VAL{PID}`。

這與第二輪在第一輪身上找到的是同一個模式：修正建立在未經檢查的前提上。

**修**：執行期的嚴格性不動；編輯器改為在預覽前替每個 `VAL{}` 相依代入樣本值 100，並在畫面上標明「預覽時以 100 代入」。驗證於是回答它真正能回答的問題 —— 這條公式**寫得對不對** —— 而不是「相依 PID 有沒有被輪詢過」。

順帶修正：編輯後若改變了 wire identity，舊項會被移除，但替換項沒有被加回儀表板 → 編輯一個錶等於刪掉它。

## 同時補上三處零覆蓋的路徑

模擬器永遠即時回應、永遠在 7E0 上，所以第二輪最精細的兩段程式碼從未被任何測試執行過。新增一個可腳本化的傳輸層來製造它們：

- 逾時 → 失步 → 重新同步 → 丟棄遲到回應（斷言遲到的 010C 回應不會被當成 010D 的答案）
- `sendOnHeader` 的換標頭分支（含「已在該標頭時不重送」與「換標頭被拒則整筆交易失敗」）
- 編輯器驗證與執行期求值對同一條 `A-VAL{0133}` 的行為差異
